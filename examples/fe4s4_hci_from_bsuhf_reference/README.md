# Running HCI (or any other solver) from the same [4Fe-4S] BS-UHF reference as our LUCJ/SQD work

## Do you need to regenerate the FCIDUMP?

No. The localized active-space FCIDUMP used for the LUCJ circuit sampled on `ibm_kingston`
(5M shots) already exists, unchanged, and was never generated by this repo -- it was supplied
directly by a collaborator (Zhendong Li), already active-space-carved (36 orbitals, 54 electrons).

    File:   fe4s4_zhendongli.txt
    Header: &FCI NORB=36, NELEC=54, MS2=0
    Size:   9,648,600 bytes
    sha256: 0b840102a4894fee4648944f2bf3bb5d85828deb4b7e71b964136bbc4c9e01ce

If you don't already have a copy, ask whoever gave you this repo for it. This script does not (and
cannot) regenerate this file from a raw molecular geometry -- no ORCA/NWChem/PySCF carve-out script
for it exists in this repo; the active-space localization was done outside this codebase.

## What this FCIDUMP alone does NOT give you

The raw FCIDUMP is just integrals in whatever MO basis the collaborator's CASSCF/localization
produced. Running plain closed-shell RHF or naive UHF on it converges to the spin-pure RHF
solution -- for a closed-shell singlet (`MS2=0`), the RHF determinant is already a stationary
point of the UHF equations, so unrestricted SCF started from the RHF density just sits there.

The actual reference used for our LUCJ sampling is a **broken-symmetry UHF (BS-UHF)** solution:
an atom-localized antiferromagnetic initial guess (the Noodleman recipe: Fe1+Fe2 spin-up,
Fe3+Fe4 spin-down, at full polarization) followed by internal-*and*-external stability-following
to the true broken-symmetry minimum. This is what actually captures the antiferromagnetic
correlation the LUCJ ansatz/SQD recovery is built on top of.

## What `prepare_bsuhf_fcidump.py` does

Standalone script (only depends on `pyscf`/`numpy`, no `qcsc-prefect` import) that:

1. Loads `fe4s4_zhendongli.txt` and reproduces the exact BS-UHF reference (same atom-localized
   AF guess + stability-following recipe as
   `algorithms/qcsc_workflow_utility/src/qcsc_workflow_utility/chem.py`'s
   `_parse_af_groups`/`_converge_broken_symmetry_uhf`).
2. Rotates the two-electron integrals into the converged BS-UHF molecular-orbital basis.
3. Writes that out as three files anyone can load into their own solver:
   - `<prefix>.alpha.fcidump` -- alpha-spin block (h1_a, (aa|aa)), standard FCIDUMP format
   - `<prefix>.beta.fcidump` -- beta-spin block (h1_b, (bb|bb)), standard FCIDUMP format
   - `<prefix>.mixed.npz` -- the (aa|bb) mixed-spin two-electron integrals (no slot for these
     in a plain FCIDUMP; needed by any UHF-based determinant solver)
   - `<prefix>.summary.txt` -- E(BS-UHF), `<S^2>`, electron/orbital counts, for a sanity check

```bash
pip install pyscf numpy
python prepare_bsuhf_fcidump.py \
    --fcidump /path/to/fe4s4_zhendongli.txt \
    --af-groups fe4s4 \
    --out-prefix fe4s4_bsuhf_p12
```

Verified (2026-08-18): reproduces `E(BS-UHF) = -327.080917 Ha`, `<S^2> = 8.877` exactly matching
the manuscript's reported reference, and the written `.alpha`/`.beta`/`.mixed` files were
independently cross-checked by reconstructing the total energy directly from them
(`-327.0809169678713` Ha, matching to 8+ decimal places).

## What this script does NOT do: it does not run HCI

**There is no HCI (heat-bath configuration interaction) solver in this repo, at any scale that
matters for [4Fe-4S].** Specifically:

- `sbd`'s native C++/CUDA solver (the one used for our SQD recovery) is a full/selected Davidson
  diagonalizer over an SQD-selected determinant subspace. It has no importance-sampling/heat-bath
  selection logic -- it cannot run HCI.
- The one HCI code path that does exist anywhere in this repo
  (`algorithms/sbd/sweep/build_fe2s2_refs.py`, using `pyscf.fci.SCI()`) is explicitly gated off
  above 24 orbitals, with the script's own comment stating why: *"Selected-CI is intractable for
  large active spaces (e.g. 4Fe-4S 36o/54e HANGS for hours)"*. It is not usable at this system's
  size.

**If you want genuine HCI on this active space**, you need an external selected-CI code capable of
36 orbitals / 54 electrons -- e.g. **Dice** (Sandeep Sharma's semistochastic heat-bath CI) or
**Arrow/SHCI**. Neither is integrated into this repo. The FCIDUMPs this script writes
(`<prefix>.alpha.fcidump` / `.beta.fcidump` / `.mixed.npz`) are exactly the inputs such a tool
would need, in the same MO basis and starting from the identical BS-UHF reference our LUCJ circuit
was sampled from -- so an HCI run on those files is directly comparable to our SQD result, the
same way our own DMRG reference (via `pyblock2`/block2, see `sqd.py`) is an external, independently
run comparison point against the identical FCIDUMP + orbitals.

## Update: running real heat-bath CI (`gdb_diag_uhf`) against this reference

The statement above ("there is no HCI solver in this repo") was true when this file was
written. It no longer is: `sbd`'s own `gdb` (General Determinant Basis) namespace ships a real
Slater-Condon heat-bath CI implementation that was simply never built or wired up -- see
`docs/reference/sbd_gdb_heatbath_and_selection_gap.md` for the full investigation and status.
That gap turned out to be a build-flag + file-format bridging problem, not a missing-solver
problem, and has now been closed for a first real smoke test:

1. **Build** `gdb_diag_uhf` (the `-D_UHF`-compiled variant of the bundled
   `chemistry_gdb_selected_basis_diagonalization` sample app):
   ```bash
   ../../algorithms/sbd/native/build_sbd_gdb_hci_uhf_fugaku.sh   # or _uhf_roquo.sh
   ```
2. **Merge** this script's three output files into the single interleaved-spin-orbital FCIDUMP
   the `-D_UHF` integral reader expects:
   ```bash
   python merge_bsuhf_to_uhf_fcidump.py --prefix fe4s4_bsuhf --out fe4s4_bsuhf.uhf.fcidump
   ```
3. **Sample** a real determinant subset from the production SQD sample pool (a saved
   `packed_bits`/`num_bits`/`num_shots` npz, e.g. `fe4s4_uhf_5M_zhendongli.npz`):
   ```bash
   python pool_to_gdb_detfile.py --pool fe4s4_uhf_5M_zhendongli.npz --norb 36 \
       --nelec-a 27 --nelec-b 27 --n-shots 5000 --out fe4s4_bsuhf_pool.detfile.txt
   ```
   This post-selects by Hamming weight before sampling -- the raw saved pool is genuine
   unfiltered hardware data, and most shots do not have the correct particle number.
4. **Run**:
   ```bash
   mpiexec -n 16 ./gdb_diag_uhf --fcidump fe4s4_bsuhf.uhf.fcidump \
       --detfiles fe4s4_bsuhf_pool.detfile.txt --do_redist_det 1 \
       --method 0 --block 10 --iteration 4 --tolerance 1.0e-4 \
       --b_comm_size 2 --t_comm_size 1 --carryovername carryover.txt \
       --carryover_type 2 --heatbath_cutoff 1.0e-4 --heatbath_truncation 10000
   ```

**Warning:** `main.cc`'s post-solve RDM-derived diagnostic energy printout (the
`"one-body energy"`/`"two-body energy"` lines near the end of its output) hardcodes an RHF-style
combination of the alpha/beta RDM blocks and is **wrong for a genuine UHF run**. Only trust the
Davidson-solved `"sbd: Energy = ..."` line -- it comes from the already-UHF-aware Hamiltonian
machinery and is unaffected. See the reference doc above for details.

This has been verified end-to-end on Fugaku with real data (not the bundled toy FCIDUMP): the
FCIDUMP merge reconstructs `E=-327.08091697 Ha` losslessly, and a live `gdb_diag_uhf` run against
200 real post-selected determinants from the production pool completed cleanly with both plain
Davidson and heat-bath expansion. Not yet done: a full-scale run, or any comparison against the
SQD trajectory at a matched subspace dimension.

## Loading a BS-UHF reference back and checking its UHF/UCCSD energy directly (no reconvergence)

**The bug this closes:** feeding the interleaved `.uhf.fcidump` file (from
`merge_bsuhf_to_uhf_fcidump.py` above) into `qcsc-prefect`'s own
`compute_molecular_integrals_from_fcidump(unrestricted=True)` does **not** load the BS-UHF
reference — that function always reruns `tools.fcidump.to_scf()` (which expects a plain
restricted-format FCIDUMP, not the interleaved spin-orbital format) and then reconverges a *fresh*
UHF from a generic guess on top of the misparsed result. Depending on `FE4S4_AF_GROUPS` (unset by
default) this can land back on the spin-pure RHF solution — this is exactly the failure a
collaborator hits when they report "`compute_molecular_integrals_from_fcidump` re-runs UHF SCF
from scratch ... falls back to RHF" after feeding it a BS-UHF-rotated interleaved FCIDUMP.

`load_uhf_fcidump_reference.py` is the fix: it parses the interleaved FCIDUMP directly (pure text
parsing, the same indexing convention as `sbd`'s `_UHF SetupIntegrals` C++ reader — no
`to_scf()`, no SCF guess, no stability-following) and evaluates the UHF energy expression by
direct tensor contraction on the file's own orbitals. There is nothing to reconverge because
there is no SCF loop at all.

```bash
pip install pyscf numpy

# UHF energy + <S^2> only (fast):
python load_uhf_fcidump_reference.py --fcidump fe4s4_bsuhf.uhf.fcidump

# also run UCCSD on top of the loaded (not reconverged) reference, for a direct comparison
# against a paper's reported BS-UCCSD number (slower, needs more memory at 36 orbitals):
python load_uhf_fcidump_reference.py --fcidump fe4s4_bsuhf.uhf.fcidump --uccsd
```

Prints `E(UHF)` [+ `E(UCCSD)` with `--uccsd`] and `<S^2>`, and writes
`<fcidump>.loaded_summary.txt` with the same numbers for a permanent, diffable record anyone can
compare against the manuscript's reported BS-UHF/BS-UCCSD energies.

**Verified correctness (2026-09-02)**, against real PySCF calculations, not just synthetic
round-trips: wrote real converged-UHF integrals (via `sbd`'s own `_write_uhf_fcidump`, the exact
function `merge_bsuhf_to_uhf_fcidump.py` calls) for two real molecules — a closed-shell N2/sto-3g
case and an open-shell OH/sto-3g (spin=1) case — then loaded each FCIDUMP back through this script
and compared against PySCF's own direct `mf.e_tot` / `mf.spin_square()` / `cc.UCCSD(mf).e_tot`:

| Case | E(UHF) match | `<S^2>` | E(UCCSD) match |
|---|---|---|---|
| N2 (closed-shell) | exact to ~1e-14 | exact | exact to ~1e-8 (UCCSD's own tolerance) |
| OH (open-shell, spin=1) | exact to ~1e-14 | 0.75 vs 0.7532619... (expected physical residual — see below) | exact to ~1e-8 |

The small `<S^2>` residual in the open-shell case is **not a bug**: this script's `<S^2>`
shortcut assumes the FCIDUMP's own MO basis is orthonormal (true by construction, since it's a
converged SCF's own canonical MOs) and uses an identity AO overlap; PySCF's own `spin_square()`
uses the real AO overlap and picks up a small amount of genuine physical spin contamination that
an identity-overlap calculation cannot see. It does not affect the energies, which match to
machine precision.

This closes the loop end-to-end: anyone reproducing the BS-UHF reference can now (1) converge it
(`prepare_bsuhf_fcidump.py`), (2) merge it into the interleaved format
(`merge_bsuhf_to_uhf_fcidump.py`), (3) load *that exact file* back and get a directly comparable
UHF **and** UCCSD energy (`load_uhf_fcidump_reference.py --uccsd`) — all three steps standalone
scripts with zero `qcsc-prefect`/Prefect dependency beyond one direct, non-Prefect function reuse
(`_write_uhf_fcidump`).

Regression tests: `algorithms/sbd/tests/test_load_uhf_fcidump_reference.py` (run with
`cd algorithms/sbd && python -m pytest tests/test_load_uhf_fcidump_reference.py -v`) — covers the
FCIDUMP round-trip, the UHF energy formula, `<S^2>`, the UCCSD path, and the CLI end-to-end, each
against a real PySCF calculation on real molecules (not synthetic data).

## Reproducing a different pairing/fragment choice

`--af-groups fe4s4` is a convenience keyword for the pairing-(1,2) reference used throughout this
work (`up={fe1,fe2}`, `down={fe3,fe4}`, full polarization). To try a different pairing or a
different molecule entirely, pass your own JSON (or `@path/to/file.json`) -- see
`docs/tutorials/run_uhf_bsuhf_any_molecule.md` Step 1 for the fragment-spec schema.
